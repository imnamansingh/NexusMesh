## Generated files and what they contain

the 'mesh' is coming from package name in proto file.

1.mesh.ph.h -> Declarations for the generated message and enum types, such as mesh::WifiNode, mesh::User, mesh::PathResponse, and mesh::Status

2.mesh.pb.cc -> implementations for those message types, including serialization and parsing.

3.mesh.grpc.pb.h -> gRPC service and client declarations. It provides mesh::MeshService::Service, which EngineServiceClass inherits from, plus client stubs.

4.mesh.grpc.pb.cc -> Implementations for the gRPC service methods, dispatch, and client-stub plumbing.

In mesh::MeshService::Service, service is none of the gRPC methods declared in proto file but it is a nested class generated by gRPC as the server implementation base. Then our EngineServiceClass inherits this class and overrides all the 5 gRPC methods to give them a defination, so the functions are defined on top of the methods declared in service class by overriding them with the help of EngineServiceClass.

## DLL Files

DLLs are Dynamic Link Libraries: shared libraries that Windows loads at runtime instead of embedding everything into one EXE.
In this service, the executable needs DLLs for:
1.Protobuf runtime: libprotobuf.dll
2.gRPC runtime: grpc.dll, grpc++.dll
3.OpenSSL / crypto support used by gRPC
4.zlib / CAres / other dependencies

all these dll files are required during runtime and windows loads them.

These files come from:
1.the vcpkg installation you used to install protobuf and gRPC
2.the build toolchain you used to compile
3.sometimes copied by the build system into the output folder

Why they mismatch:
1.the EXE was built with one set of libraries
2.but Windows loads another set from a different folder
3.or a Debug build loads Release DLLs, or vice versa
4.or an old DLL remains in the output folder from a previous build

Where to find them:
1.In your repo: bin
2.Also under Engine/build/Debug or Engine/build/Release if copied there by the project

The clean rule is:
1.build config and DLLs must match
2.use the DLLs from the same vcpkg triplet and same build type
3.keep only one set in the same output directory

vcpkg intalls related dll files also when you install a package and these files are required during runtime so you need to copy them in the build folder.

In Cmake config file, you need to tell the Cmake to copy the required dll files from specified folder to the build folder after the building process of project completes.
example code:
add_custom_command(TARGET EngineService POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_directory
    "D:/PROJECTS/NexusMesh/Engine/vcpkg_installed/x64-windows/bin"
    $<TARGET_FILE_DIR:EngineService>
)

debug vs release dlls:
“Debug” and “Release” DLLs are two builds of the same dependency libraries, compiled for different build configurations.
Debug DLLs are built for debugging: typically less optimized, with extra checks and debug-runtime dependencies. They’re intended to be used by a Debug executable.
Release DLLs are optimized for normal use and are intended to be used by a Release executable.
